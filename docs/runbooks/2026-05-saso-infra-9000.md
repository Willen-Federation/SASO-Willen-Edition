# Runbook: 本番 `saso.sksl.jp` の `/api/v1/*` が SASO-INFRA-9000 で全滅

最終更新: 2026-05-23

## 1. 何が起きていたか

iOS クライアント (SASO-Willen-Edition-Flutter) でログイン後にアイテム検索・編集・追加・保管場所表示などのボタンを押すと、画面に下記のメッセージが出てすべての操作が失敗していた。

```
ProblemDetails(500, SASO-INFRA-9000): Internal server error —
An unexpected error occurred. Reference: <UUID>.
```

`curl` で本番に直接当てた結果 (2026-05-22):

| Endpoint | 結果 |
|---|---|
| `GET /api/v1/health` | **200 OK** (サーバーは生きている) |
| `GET /api/v1/auth/providers` | **500** `SASO-INFRA-9000` |
| `GET /api/v1/items` | **500** `SASO-INFRA-9000` |
| `GET /api/v1/storage-locations` | **500** `SASO-INFRA-9000` |
| `GET /category/list.json` (Legacy) | 200 OK + Set-Cookie |

## 2. 根本原因

### 原因 (A): 認証層が `RuntimeException` を漏らしていた【コードバグ】

`JwtGuard::authenticate()` および `JwtService::verify()` は、Bearer ヘッダー欠落・署名不正・トークン期限切れなどあらゆる認証失敗で plain `RuntimeException` を投げていた。

`ProblemExceptionHandler` は `DomainException` 派生だけを認識し、それ以外を `SASO-INFRA-9000` (500) にマップする設計だったため:

- `/api/v1/items` (要 JWT) — 未認証アクセス → 本来 401 を返すべきが 500
- `/api/v1/storage-locations` (要 JWT) — 同上
- 他、JWT を要求する全エンドポイント (config bundle、token refresh以外、PATCH items 等)

そして Flutter クライアントはエラーボディが「500 / SASO-INFRA-9000」だと「サーバー側の致命的不具合」として ProblemDetails をそのまま画面に表示する。これが「全ボタンでサーバーエラー」の正体。

**該当ファイル**:
- [`src/Application/Mobile/JwtGuard.php`](https://github.com/Willen-Federation/SASO-Willen-Edition/blob/main/src/Application/Mobile/JwtGuard.php)
- [`src/Domain/MobileConnect/Jwt/JwtService.php`](https://github.com/Willen-Federation/SASO-Willen-Edition/blob/main/src/Domain/MobileConnect/Jwt/JwtService.php) (こちらは未修整。今は JwtGuard で wrap)

### 原因 (B): Discovery エンドポイントが脆い hydrate に依存【コードバグ + データ問題の合わせ技】

`GET /api/v1/auth/providers` は **未認証で公開**されている。にもかかわらず 500 を返していた。

`PdoAuthProviderRepository::listEnabled()` が呼ばれると、すべての enabled 行で `hydrate()` を実行し、その中で `SecretEncryptor::decrypt(client_secret_encrypted)` を eager に実行する。本番の `auth_provider` テーブルに **過去の `APP_KEY` で暗号化された** 行が残っていると、復号で `RuntimeException` が飛び、それが (A) と同じ理由で `SASO-INFRA-9000` に化ける。

しかも Discovery エンドポイントのレスポンスには `client_secret` は出さない (機微情報なので非公開)。**復号する必要すらない**情報のために、テーブル全体のロードが落ちていたという形。

**該当ファイル**:
- [`src/Infrastructure/Auth/Repository/PdoAuthProviderRepository.php`](https://github.com/Willen-Federation/SASO-Willen-Edition/blob/main/src/Infrastructure/Auth/Repository/PdoAuthProviderRepository.php)

## 3. 修正内容 (このブランチで入っているもの)

ブランチ: `fix/api-v1-auth-required-mapping`

### 修正 1: `AuthRequiredException` を新設し、`JwtGuard` で使う

- 新規: [`src/Domain/Auth/Exception/AuthRequiredException.php`](https://github.com/Willen-Federation/SASO-Willen-Edition/blob/main/src/Domain/Auth/Exception/AuthRequiredException.php)
  - `DomainException` 派生、`ErrorCode::AuthUnauthorized` (SASO-AUTH-1004、HTTP 401) にマップ
  - `missing()` ファクトリ: ヘッダー欠落用
  - `invalidToken(string, ?Throwable)` ファクトリ: トークン検証失敗用 (原因 RuntimeException は `$previous` に保持される → ログには「invalid signature」「token has expired」など具体的な原因が残る)
- 修正: [`src/Application/Mobile/JwtGuard.php`](https://github.com/Willen-Federation/SASO-Willen-Edition/blob/main/src/Application/Mobile/JwtGuard.php)
  - ヘッダー欠落 → `AuthRequiredException::missing()`
  - `$this->jwt->verify($token)` の `RuntimeException` を catch して `AuthRequiredException::invalidToken` に再 throw

これだけで `/api/v1/items`、`/api/v1/storage-locations` などすべての JWT 必須エンドポイントが正しく **401** を返すようになる。クライアント (Flutter) 側は元から 401 を「Authentication failed」として静かに扱うので、画面の SASO-INFRA-9000 メッセージは消える。

### 修正 2: `PdoAuthProviderRepository::hydrateAll()` のレジリエンス化

- 修正: [`src/Infrastructure/Auth/Repository/PdoAuthProviderRepository.php`](https://github.com/Willen-Federation/SASO-Willen-Edition/blob/main/src/Infrastructure/Auth/Repository/PdoAuthProviderRepository.php)
  - hydrate に失敗した行を catch + `error_log` で記録し、残りの行は返す
  - 1行壊れていても `/api/v1/auth/providers` 全体は 200 で返るようになる
  - ログ行のフォーマット: `[PdoAuthProviderRepository] skipping unhydratable auth_provider row (id=X): <reason>`

### 修正 3: テスト

- 修正: `tests/Unit/Application/Mobile/JwtGuardTest.php` — 新例外を期待するように tighten + 改ざんトークンが 401 に化ける新テスト追加
- 修正: `tests/Unit/Infrastructure/Auth/Repository/PdoAuthProviderRepositoryTest.php` — 異なる APP_KEY で暗号化された行を 1 件混ぜても残り 2 件は返る、を verify

### 既知の time-bomb (本修正と無関係)

`JwtGuardTest` の 3 errors + 1 failure は、テストが固定日付 `2026-05-17` で JWT を発行・現実時刻で verify するため発生する既存問題。main にも同じ失敗があり今回の修正は触っていない。別 PR で `JwtService::verify(?DateTimeImmutable $now)` を活用するよう書き換えるのが筋。


## 5. データ側の追加対応 (運営側で確認が必要)

修正 2 (hydrate のレジリエンス化) で `/api/v1/auth/providers` は復旧するが、**壊れた `auth_provider` 行が残ったまま**になる。本番の admin 画面 (`/mypage/devicePair`、認証プロバイダー一覧) では当該行が出ないので、放置すると気付かない。デプロイ直後に下記をやる:

### 5.1 PHP のエラーログから対象行を特定

```bash
# 本番サーバー (saso.sksl.jp) に SSH 接続後
ssh saso.sksl.jp
tail -n 200 /var/log/saso/php-error.log | grep "skipping unhydratable auth_provider"
# 期待される行例:
# [PdoAuthProviderRepository] skipping unhydratable auth_provider row (id=3): SecretEncryptor: openssl_decrypt failed.
```

行 id を控える(例 `id=3`)。

### 5.2 DB を直接確認

```sql
-- 該当行のメタデータを確認 (secret 自体は触らない)
SELECT id, name, type, enabled, is_default, created_at, updated_at
FROM auth_provider
WHERE id = 3;

-- 同 APP_KEY で書かれた行と区別するために、enabled な全行を一覧
SELECT id, name, type, enabled, created_at FROM auth_provider ORDER BY id;
```

### 5.3 対応方針(3択。実機サポート前にチームで決定する)

| 方針 | 操作 | 適用条件 |
|---|---|---|
| A. 再設定 | admin UI (`/mypage/auth_provider`) で当該 provider を編集し、client_secret を入力し直して保存 | 該当 IdP の client_secret が手元にあり、本番で使うつもりがある |
| B. 無効化 | `UPDATE auth_provider SET enabled = 0 WHERE id = 3;` | 一時的に隠したい(復旧待ち) |
| C. 削除 | `DELETE FROM auth_provider WHERE id = 3;` | もう使わない、または再投入予定 |

操作前に念のためバックアップ:

```bash
mysqldump --single-transaction saso auth_provider > /tmp/auth_provider_backup_$(date +%Y%m%d_%H%M%S).sql
```

### 5.4 もし `APP_KEY` がローテーションされていた場合

`SecretEncryptor::decrypt()` が落ちる原因は `APP_KEY` がローテートされて旧鍵で暗号化された行が読めなくなっているケースがほとんど。確実に旧 APP_KEY が分かるなら、

1. 旧 APP_KEY で復号 → 現 APP_KEY で再暗号化するワンショットスクリプトを書く(`migrations/` に倣う形)
2. 行ごとに `UPDATE auth_provider SET client_secret_encrypted = :new WHERE id = X;`

旧 APP_KEY が不明 (ローテーション履歴が残っていない) なら方針 A (再入力) しかない。

## 7. クライアント側の対応

Flutter リポ ([SASO-Willen-Edition-Flutter](https://github.com/willen-jp/SASO-Willen-Edition-Flutter)) 側は今回 **無修正**で OK。理由:

- `RestV1ApiClient._handleErrors` はすでに `application/problem+json` を正しくパースしている
- `ErrorDisplayWidget` の `error.toString()` は ProblemDetails が 401/SASO-AUTH-1004 になれば「セッション切れ」として静かにログイン画面へ戻す既存の AuthInterceptor 経路に乗る
- 暫定回避策として「設定画面で ApiMode を Legacy に切り替えれば、検索系は復旧する(編集・追加・保管場所は Legacy 未対応)」も使えるが、本修正後は不要

サーバー修正をデプロイしたら、Flutter 側は**そのまま使える**。
